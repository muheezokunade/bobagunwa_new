# Page Inventory and Route Verification Register

Last updated: 14 October 2026

This document is the source of truth for route coverage. A route may be marked **Complete** only when its interface, navigation, access control, persistent backend integration, responsive behaviour, and automated tests are all verified. A rendered page backed only by fixtures or simulated data remains **Partial**.

## Status and test conventions

- **Existing / partial** — the route renders, but content, persistence, workflow, authorisation, or test coverage is incomplete.
- **Foundation** — supporting schema or service code exists, but the route is not yet a complete user workflow.
- **Planned** — the required end-to-end workflow is not implemented. A guarded read-only route shell may exist, but it is not counted as complete.
- **Blocked** — implementation depends on a recorded decision or unavailable platform capability.
- **Complete** — production-capable implementation and all required checks pass.
- State abbreviations used below: **L** loading, **Ø** empty, **E** error with recovery action, **S** successful action confirmation.
- Test abbreviations: **R** route/build, **N** navigation, **I** integration/database, **A** authorisation, **V** validation, **M** mobile/responsive.

## Shared requirements

All routes use the organisation's approved identity, logo and colours; retain visible keyboard focus; meet WCAG 2.1 AA contrast; provide semantic headings and landmarks; and use the shared responsive header/footer or the appropriate portal shell. Public routes collapse to a touch-friendly navigation on narrow screens. Portal and administrative data tables become cards or horizontally scrollable tables with labelled controls on mobile. Destructive actions require explicit confirmation and are recorded in the audit log.

On 15 October 2026, all 52 substantive page views passed automated browser checks at 320×800, 768×1024 and 1440×900 for their intended public, member or administrator role. The checks covered landmarks/headings, horizontal overflow, image alternatives, visible form labels, button names and password-form methods. `/portal` and `/portal/logout` are redirect/action routes covered by the live authentication suite. Manual keyboard, screen-reader, browser-matrix and final-origin acceptance remain open, so no route is promoted to Complete by this result alone.

Anonymous users may access only the public and authentication routes. Members may access only their own portal records. Administrative access is permission-based rather than inferred from navigation visibility. Direct URL access is denied server-side when the session or permission is insufficient.

## Intentional consolidation decisions

- Create actions that need a full review workflow have dedicated routes (`assessments/new`, `payments/new`, member import). Simpler creation may begin from the module list and continue on the canonical detail route.
- Public news and public event details are separate from portal announcements/events because publication and audience rules differ.
- Member financial balances and printable statements share the same ledger service, but remain separate routes so both workflows are directly accessible.
- Backup operations are surfaced separately from general settings because restore authority and operational risk are materially different.

## Automated verification gates

The following gates must all pass before the inventory can be reported complete:

1. Route manifest test proves every inventory route has a matching page implementation, including dynamic-route samples.
2. Navigation crawler proves every required workflow is reachable and finds no broken internal links.
3. Anonymous checks prove public/auth pages work and all portal/admin routes deny direct access.
4. Member checks prove portal pages work with persisted records and prevent cross-member access.
5. Administrator checks prove permitted actions work and non-permitted actions fail at the backend.
6. Database integration tests run against a migrated test database and verify durable writes, finance invariants, audit events and idempotency.
7. Responsive checks cover representative mobile and desktop widths for every route family.
8. Build, type-check, lint, unit, integration and security-focused tests pass without critical findings.
